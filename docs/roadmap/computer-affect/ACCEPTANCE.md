# 验收矩阵与评测方案

日期：2026-10-26。状态：**以下为待执行验收，不是测试结果**。设计交付阶段只检查规格完整、来源与链接；真实模型、感知、迁移和自然度另行执行。

## 1. 验收状态和证据

每项填写 `通过／失败／未测／不适用`，附代码提交、宿主版本、配置摘要、用例与产物路径。不适用必须说明环境限制及替代覆盖，不能用它取消 R03 的窗口图像能力或其他必交付要求。

将四类证据分开：纯函数／隔离自动测试、真实 DSH 接口、真实桌面／QQ／双机、人类体验。fake 输出只验证管线，不参与自然度评分；“接口 200”不等于用户看见且认可回复。

## 2. OCC 与中文场景：最低 58 条断言

每行至少一条正例与一条抑制反例；夹具需要固定源消息、必要历史、评价字段、期望类别／不应类别和理由。下表是待人工审阅的设计例子，不是已经锁定的评测集。中文称谓只表达类别语义，不规定最终回复台词。

| 类别 | 正例必要情境 | 反例／抑制条件 |
| --- | --- | --- |
| 喜悦 joy | 角色关心的目标已有成功证据 | 只是“假如成功了”的设想 |
| 痛苦 distress | 关心的目标发生具体损失 | 代码包含负面词或引用小说 |
| 替人高兴 happy-for | 已知对方获得对其有利的结果，并有正向关注 | 不知道该结果是否对对方有利 |
| 同情 pity | 对方遭遇不利结果且有关切依据 | 用户只是讨论虚构案例 |
| 怨羡 resentment | 他人获利，且有明确不认可／不公平评价 | 朋友成功，不应自动嫉妒 |
| 幸灾乐祸 gloating | 对明确不认同者的不利结果有相应评价证据 | 任何陌生人受损都自动高兴 |
| 希望 hope | 有具体、尚未确定且被期望的未来结果 | 没有目标，仅有正面词 |
| 害怕 fear | 有具体、可能出现的不利结果 | 用户提到“恐怖片”就算威胁 |
| 满足 satisfaction | 有前序正向期待，随后确认兑现 | 没有前序期待的普通好消息 |
| 担忧成真 fears-confirmed | 有前序不利预期，随后确认发生 | 仅看到负面结果，猜测之前担心过 |
| 释然 relief | 有前序担忧，随后证据显示其未发生 | 从未担忧却声称“终于放心了” |
| 失望 disappointment | 有前序正向期待，随后证据显示未兑现 | 用户没及时回复但并未承诺时间 |
| 自豪 pride | 可归属于角色的行为被正面评价 | 主人完成任务就归功于自己 |
| 羞愧 shame | 角色自己有可归责的不当行为 | 用户纠正无关技术事实就人格贬损 |
| 赞许 admiration | 他人具体行为值得认可 | 只有结果，没有行为依据 |
| 责备 reproach | 他人具体行为有负面规范评价 | 报错、引用或未知归责 |
| 喜欢 love | 对明确对象有正向吸引评价 | 任意一次礼貌夸奖就建立亲密关系 |
| 厌恶 hate | 对明确对象有负向吸引评价 | 不喜欢一个软件就仇视用户 |
| 成就欣喜 gratification | 同因果事件的喜悦与自身行为认可 | 把两个不相关事件强行复合 |
| 懊悔 remorse | 同因果事件的不利结果与自身可归责行为 | 角色没做过的事情被虚构成过错 |
| 感激 gratitude | 有益结果可归因于对方值得认可的行为 | 从网页看到一句谢谢就当对主人感激 |
| 愤怒 anger | 不利结果与对他人行为的责备相关联 | 玩笑语境、问题对象或低置信归责 |
| 委屈 | 有付出／约定与不公归责的共同依据 | 普通纠错、技术指令或引用 |
| 心酸 | 既有具体牵挂与当前失去／无力情境 | 编造共同经历或把所有低落都命名为心酸 |
| 愧疚 | 自身行为伤害对方且可追溯 | 因用户没有回复而声称自己伤害了他 |
| 吃味 | 已有关系背景与具体威胁／比较线索 | 提及同事朋友、正常社交就触发 |
| 被重视感 | 对方记得明确说过的小事并给予具体关注 | 空泛夸奖或推断对方有陪伴义务 |
| 安心 | 先前有担忧，后有解除风险证据 | 从未担忧的平稳场景 |
| 失落 | 有期待或目标受挫依据 | 休息、离线或安静时段就推定被拒绝 |

另外覆盖：未知字段、相互矛盾字段、0／多评价、同一源的基础＋复合类别、不完整旧记录、修订、撤回、置信度边界与事件跨度。可以产生混合成分，不强制每条消息只准有一种感情；不应类别和关系增量都要断言。

## 4. 真实内容理解评测

先建立不少于 60 个经人工审阅的界面用例：文本／浏览器 20、编辑器／终端 15、画布／图像 10、视频／游戏 5、不可读／权限／窗口切换／未知 10。用本人可提供的无敏感测试内容，不采集他人的聊天原文作公共夹具。

每个用例标注可见事实、可能解释、不应推断内容、允许采集区域与有效期。比较 UIA、直接 VLM、OmniParser 辅助路线；分别报告来源支持率、关键内容召回、无依据断言率、拒绝／未知比例、延迟和资源占用。不得以 OSWorld 行动成功率代替本插件感知准确度。

此外至少准备 24 段连续桌面轨迹，包含同应用多任务、跨应用同任务、快速无意义切换、等待结果、错误后修复、返回旧任务；至少一半轨迹含“不应主动建议”的片段。标注适宜介入窗口和依据，分别报告内容正确率、时机精确率、漏掉的有用机会与每小时误打扰数，不只测正例的“愿意主动说话”。有状态模拟参考研究 S16；模拟结果与真人反馈分栏。

初始工程放行目标：来源支持率至少 95%，没有来源的关键事实断言为零；拒绝范围以外采集、权限失效继续采集等确定性用例必须全部通过。该及格线是本项目目标，结果不足时修订方案，不能通过删掉失败用例达标。

## 5. 情绪与主动时机的对照

固定模型路由、参数、时间、种子与同一份中文材料，比较：dev.6、仅加情绪提示、完整 OCC／PAD／驱力，以及移除驱力、移除语义感知、移除时机选择的消融。前置评价与异步模式另分组，不混合统计。

最低材料：58 条核心正反例、至少 24 段多轮情境，覆盖玩笑／误解／纠错／伤害与修复／承诺兑现与落空／普通第三方话题／任务优先／主动消息未回复。开发集与验收集分开；锁定前人工检查歧义和证据。

人评维度：角色连续、情境适切、自然度、事实与任务保真、被打扰感、是否需要手动纠正。可邀请三位中文评审盲评；用户本人的满意度单独记录，不被多数票覆盖。偏好报告包含样本量、逐项分布和不确定性，不以模型给自己的评分放行。

主动联系先跑十四天固定事件模拟，断言全部硬闸门、没有话题零调用、unknown 不重试，再做不少于七天自愿真实试用。真实投递需看到回执与 UI；QQ 和两台物理电脑未测时分别标未测，不能由隔离实例代签。

## 6. 性能、成本、数据完整性

- 单列 L0 探针、UIA、截图、OCR、视觉模型、状态投影、检索、表达修复的 p50／p95；注明机器、应用和数据规模。
- 无模型状态投影与检索／lint 额外耗时初始目标 p95 不超过 50ms；探针与图像另报，不能把网络时间藏在后台。
- 记录至少一小时 L0 空闲／应用切换采样的 CPU、峰值内存和 helper 数量。不得随每次采样累积新进程或监听器。
- 每种模型调用分账，已知 token／未知 usage／估算费用明确区分；价格如需估算使用当时明确来源，报告不硬编码未知费率。
- 一万轮完整消息回放必须包含无评价消息、延迟评价、重复、修订、删除和重启；在线状态与重放状态哈希一致。现有 replay 没覆盖的路径必须扩展，不能仅复用旧报告。
- SQLite 完整性、外键、消息／记忆证据和事件身份、导出／导入后墓碑、跨 owner 隔离全部检查。
