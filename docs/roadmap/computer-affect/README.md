## 本机抽取问题的核查结论

本次只读核查发现：

- 当前模型配置已经包含 `reasoningEfforts.off: null`，不是仍然没有 `off`。
- 已安装 DSH 的 `dsh-llm-pi-ai` 将这个声明解释为支持 `off`、发出请求时省略相应思考参数。它与填入字符串值的映射不同。
- 插件 `streamFromHost` 查询 `resolveModelInfo().reasoning.efforts`，可以识别 `none`、`off`、`disabled`。早先的严格实现找不到这些档位时，在发起模型请求前就抛错；当时的失败不是模型返回的抽取 JSON 不合格。
- 库中三条 `extract` 任务各尝试三次后进入 `failed`，发生时间均早于当前 profile 的配置更新时间。失败队列不会因为增加模型档位而自动重新执行。
- 当前挂载实例的后台计数已重新开始，最近错误为空；没有新的成功抽取证据。**历史失败不等于添加 `off` 后依然失败，也不能据此宣布已经修好。**
- 工作区 `src/adapters/dsh-adapter.ts` 及对应编译文件已有一份将“无关闭档位”回退到默认档的未提交修改；本次保留，不覆盖。这份磁盘修改是否进入旧进程的模块缓存，不能仅由文件存在推断。

定位入口：`src/adapters/dsh-adapter.ts::streamFromHost`、`src/adapters/local-integration.ts` 中的 extract handler、`src/runtime/background-queue.ts` 的终止重试逻辑。宿主实装代码的 `resolveModelReasoning` 和 `reasoningInfo` 也已核对；不把其他版本的接口当成本机事实。

`off: null` 证明的是宿主如何构造请求。上游服务在不传思考参数时是否真的不思考，要由该服务的协议和一次实际请求确认，不能由菜单名称保证。

本次另以不联网的假宿主验证：声明中含 off、前台选择 high、后台请求 disabled 时，当前磁盘构建将 `reasoningEffort: off` 传给宿主。断言通过，外部模型调用为零；该检查不代替运行中实例的一次成功抽取。

后续修复验收应先确认运行中的能力声明，再对有原文且未删除的历史失败任务执行一次有记录、有限次的恢复，并检查新的任务结果、记忆证据和情感事件。不要清空库、重放已成功任务或无限重排失败任务。本次没有修改队列或发送试聊消息。
