# 双设备首次配对验证（0.3.0-dev.8，2026-10-27）

本轮验证针对“两台属于同一真实用户的电脑各自初始化、两边都有重要记忆”的首次配对，不使用覆盖或清空恢复。日常同 owner 离线合并仍沿用原同步流程。

## 自动验证

从 Git index 生成独立发布副本，在该副本构建并运行所有测试：

```powershell
node scripts/build.mjs
node --test "tests/**/*.test.mjs"
```

结果：**432 项通过，0 失败、0 取消、0 跳过**。本机记录为 `artifacts/owner-dev8-release-20261027/artifacts/release-tests.tap`，编译产物 267 个文件。该副本未包含开发目录中的 drive、round3 等未发布草稿；对应 lib 由该副本生成。此前 dev.7 的 421 项验证也已通过；dev.8 额外加入 11 项跨版本保护回归。

主要新覆盖：

- 两份非空库的预览逐表回滚，预览不创建备份；普通导入仍拒绝不同 owner。
- 明确确认采用来源 owner，单事务归并并保留双方消息、事实和情感事件；合并前备份仍保持原 owner 和原始数据。
- 包指纹、本地指纹、备份后其他连接写入、预览有效期、活动生成/后台/发送闸；异常回滚全部表。
- 严重 ID 冲突阻断；删除事件优先、不把来源“全删”扩大为另一端新历史；合并包往返和恢复重放仍保护删除。
- 真实 MemoryTransfer 加模拟网盘：首次配对、B 上传后 A 导入、两端继续新增、多轮同步、重复同步不重复计分，最终关系数值收敛。
- 本机真实 HTTP 控制台：普通导入 409、预览和确认分离、错误确认/过期输入拒绝、页面脚本语法。网盘启动检查未结束时本地文件预览仍返回；云端预览不暗中执行同步，不覆盖正在同步的 transport。
- 归并后 Desktop 已注册会话使用新 principal，仍向原会话投递。
- 旧 principal 的传递别名继续派生原记忆 ID，整理相同事实只追加证据；旧 bare memoryId 删除和现代 suppression 均不复活，另一主人的行不被复用。
- 归并后的库使用 v3 封装和 payload，最低读版本 dev.8；旧版仅允许 v1/v2，会在写入前拒绝 v3。新版本仍读旧包，无归并标记或别名的普通库仍导出 v2。v3 的保护标记在恢复和往返后保留，不会被 v2 对端删除或设为 0 而降级；已有归并别名的旧库也会升级导出格式。

DSH 参与了两轮只读复核。关于旧 ID 的问题使用临时库实际复现后修复；关于现代 suppression 普遍失效的推断已由控制组排除。未以静态意见代替回归结果。

## 实际使用的界限

没有读取、修改或上传两台真实电脑的记忆，本轮未声称物理双机已经同步。首次配对需要用户核对来源，在新版控制台明确确认同一真实用户；两台电脑均须使用 dev.8 或兼容新版本，以及同一伴侣标识。实际流程见 [双设备记忆合并](CLOUD_MEMORY_SYNC.md)。

同 ID 异文的自动拆分未实现；此类输入会停止并保留双方原件。没有提供合并后的一键撤销；合并前备份保留证据，已有新聊天时不可直接用旧库覆盖。性格分支或设置差异会记录冲突，不能将有冲突的结果称为完全一致。

2026-10-27 用户重启后，实际诊断和管理页已确认加载 dev.8，三个首次配对控件可见。随后通过原客户端验证百度授权、列目录和下载正常，但一份 SHA256 正确的对端包声明 schema 8，并含 `emotion_appraisals`、`emotion_appraisal_revisions`、`response_events`；本机源码只有迁移 001–007，不能完整读取该分支的情感扩展。两端 owner 相同，因此现场问题是程序结构不同，不应再次 adopt 身份。

该包没有附带插件代码；本机及当前远端分支中也没有相应 008 迁移。已保留云端原件并额外导出本机记忆，未覆盖远端或执行身份归并。继续处理需另一端交接完整源码和原始迁移，先在副本验证升级及增量合并。432 项自动回归不构成这一未知扩展分支已兼容的证据。
