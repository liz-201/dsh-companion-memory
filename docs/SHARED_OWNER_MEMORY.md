# 唯一共享的情感记忆

0.3.0-dev.6 修正此前按宿主人设创建独立记忆主体的实现。需求是所有本人的对话共用一份连续的情感记忆。

## 现在的行为

- 同一位用户的所有 DSH 窗口、模型、人设和已绑定的本人私聊，使用同一个 owner 主体。
- 情感、关系、性格、长期记忆、交流习惯和兴趣只有一份。新开窗口、编辑人设、切换模型不会清零或拆分这些数据。
- 宿主当前人设仍负责当前回复的角色表达；它不再决定情感记忆存储位置。
- 对话编号继续保留，记录原文来源和提醒投递位置。控制台切换会话时，看到的是同一份记忆与状态。
- 主动联系的未回复暂停也跨窗口共享。在一个窗口没有回复，不会在另一个窗口再来一条；在另一个窗口回复后，所有窗口都能识别这一事实。

## 旧数据如何处理

正常重启加载修复版即可，无需手动导出或拼接文件。程序在迁移前创建 SQLite 一致性备份，再在一个事务中完成归并；出错会全部回滚。

旧人设分区中的原文、记忆、来源引用、情感事件、习惯、提醒及撤回/删除记录都保留。原文和记忆内容不会改写，来源编号不变。情感按全部有效历史事件按时间重新投影，不把各分区的初始好感重复相加；晚于合并历史的旧基线会重新定位，避免在已积累状态上重复叠加旧事件。

所有旧快照和相关设置会留在本机迁移归档中。若某份旧快照没有可回放的事件，程序记录这一情况；完全没有事件时保留最近的有效快照，有完整事件时以事件历史为依据，不猜测缺失的经历。恢复备份可还原迁移前状态。

再次启动不会重复迁移；导入旧版分区记忆包时，在导入的同一事务中归一，避免重新分裂。导入前的备份和原有校验继续有效。身份归并只针对已经确认属于同一 owner 的分区，不把另一个人的数据混进来。

实现入口是 `OwnerIdentity.binding`、`unifyOwnerState` 与 `importPortable`。本次不修改已应用的 SQL 迁移，使用现有事务、备份与设置表保存归档。

## 验证

新增回归覆盖窗口/模型/人设切换后共享状态，跨窗口回忆与习惯，旧分区合并、重复启动、旧包导入和重复导入、备份及事务回滚、旧基线重定位、无事件快照保留、另一个 owner 的保护，以及跨窗口未回复暂停。

独立发布快照全量 300 项通过，0 失败、0 跳过；工作目录连同另外保留的云端改动共 313 项通过。本轮提交不包含那些既有的云端改动。

真实正在使用的库通过只读连接建立一致性副本，再在副本迁移和导出恢复。最近一次验证包含 422 条原文、140 条记忆和 20 条情感事件：内容、事件编号与撤回状态一致，原分区归一后只有一个共享情感状态，外键和 SQLite 完整性检查通过。该验证没有修改生产库。

用户重启后，实际 DSH 已加载 dev.6。现有 23 个控制台会话均引用同一个主体并读取相同的记忆。另用只读连接逐项比对启动时自动生成的恢复备份：迁移前 423 条原文、140 条记忆、20 条情感事件全部保留，原文内容及来源、记忆内容、事件编号和撤回状态一致。旧分区为 0，共享情感快照为 1，外键和完整性检查通过。百度启动同步已完成，错误与冲突均为 0。

控制台路由、按钮脚本、设置校验、原生自检和启动入口描述均已验证。当前电脑截图工具不可用，界面外观由人工查看；人类对交流自然度的评价仍与存储一致性分开验收。
